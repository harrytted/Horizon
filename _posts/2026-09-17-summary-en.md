## [4B model trained to generate query plans 81% faster than Postgres](https://rohanbansal.com/qorl) ⭐️ 8.0/10

A blog post on rohanbansal.com describes training a 4-billion-parameter model to produce query plans that its author claims run 81% faster than those generated by Postgres. The post drew 454 upvotes and 94 comments on Hacker News, where commenters focused heavily on benchmark methodology rather than the raw speedup number. It is a novel demonstration that a small, locally runnable language model can be applied to database query optimization, a task traditionally handled by hand-written cost-based heuristics inside the planner. If the approach generalizes, it could reshape how optimizers are built and lower the barrier to workload-specific tuning, but the critical reception also shows how much skepticism such performance claims face. Commenters noted the benchmark used an 8 GB dataset that fits entirely in memory, with shared_buffers constrained to a fraction of that size, warmed caches, read-only SELECT queries, and no secondary indexes or extra column statistics beyond primary keys. Those conditions make it hard to tell whether the learned plans would beat Postgres heuristics on larger, more realistic OLTP workloads, and no evidence was presented about the risk of hallucinated plans causing regressions in production.

hackernews · polyphilz · Sep 16, 18:50 · [Discussion](https://news.ycombinator.com/item?id=49731285)

**Background**: A query plan is the set of instructions a database follows to execute a SQL query, and it is produced by the query optimizer, which normally estimates costs from table statistics and index availability. Language models with roughly 4 billion parameters, such as small Gemma variants, are compact enough to run on laptops or edge devices, which is why using one as a planner is notable. Benchmark realism is a recurring concern in machine learning: a benchmark is only meaningful if the conditions it tests resemble what actually happens in production, and it is also easier to reproduce when the setup is simple and controlled.

## [New Method Compresses Ternary LLM Weights to 1.48 Bits](https://arxiv.org/abs/2609.16338) ⭐️ 8.0/10

A new quantization technique pushes ternary LLM weights below the well-known 1.58-bit bound, reaching roughly 1.48 bits per weight by exploiting the fact that real ternary weights are zero about 51% of the time. The work targets more efficient embedded inference and custom silicon rather than standard GPU deployment. If ternary models are eventually baked into dedicated hardware, squeezing weights below log2(3) could cut memory footprint and power consumption further, making large models genuinely portable for on-device and embedded use. It also signals continued academic interest in extreme quantization as an alternative to the floating-point-heavy GPU status quo. The gain applies mainly to the stored model format: at inference time the compressed weights must still be expanded back into the conventional ternary representation (about 5 trits per byte), so the benefit is in file size and memory bandwidth rather than in the arithmetic itself. Community experts also caution that ternary quantization is not obviously the best choice in this bit regime, where vector quantization and trellis-based post-training quantization methods often perform better.

hackernews · matt_d · Sep 16, 20:59 · [Discussion](https://news.ycombinator.com/item?id=49732931)

**Background**: Ternary LLMs store each weight as one of three values, -1, 0 or +1, which theoretically requires log2(3) ≈ 1.58 bits per parameter — the basis for the name of Microsoft's BitNet b1.58, which showed a 1.58-bit model could match 16-bit baselines. Because multiplying by -1, 0 or +1 is trivial, such models eliminate most floating-point multiplications, making them attractive for CPUs, FPGAs and ASICs. Post-training quantization (PTQ) compresses an already-trained model, while quantization-aware training (QAT) trains the model knowing it will be quantized; the two differ substantially in achievable quality.

Security researchers disclosed that Flock Safety's license-plate-reading cameras contain hardcoded API credentials and other insecure-by-design flaws, and that Flock's vulnerability disclosure policy is written to discourage genuine security reporting. The write-up by Micah Lee details how a hardcoded API key can be used to request plaintext-stored credentials that appear to grant access to Flock's backend servers. Flock cameras are deployed in thousands of US cities and neighborhoods, so flaws that allow local physical or credential-based access threaten the privacy of vehicle-location data collected on a massive scale. The case also highlights how surveillance vendors' security posture directly shapes public trust and the growing backlash against ALPR deployments. The exposed secret was an API key rather than a hardcoded admin password, and it is not yet clear what an authenticated attacker could actually do as a camera; Flock's vulnerability disclosure policy explicitly excludes cases that require interacting with the device or downloading its data. Community analysis further notes that device data appears to be stored without adequate encryption, making physical access a viable attack path.

**Background**: Flock Safety builds automated license plate readers (ALPRs) — AI-powered cameras that photograph and log the plate, make, and location of every passing vehicle, with data cross-referenced against watchlists such as stolen-vehicle and AMBER alert databases. Hardcoded credentials (catalogued as CWE-798) are a classic weakness in which passwords or keys are baked into firmware and can be extracted by anyone with physical or firmware access. A vulnerability disclosure policy (VDP) is the formal channel through which vendors invite researchers to report flaws, and a restrictive one can effectively discourage disclosure.

If such submissions scale, journals and conferences will face higher reviewing costs, harder integrity enforcement, and eroding trust in published ML research. The check was an unusual, human-centered intervention: instead of relying on AI-text detectors, whose reliability is widely disputed, the Co-EiC conducted live interviews and asked authors to explain their own submissions. The evidence base is small and anecdotal — only 10 papers, all drawn from a single venue's desk-rejection shortlist — so the results are suggestive of a pattern rather than statistically representative of ML submissions as a whole.

Sina Cloud SAE (Sina App Engine), China's first PaaS cloud platform, is being permanently taken offline at midnight on September 16, 2026, and all user data stored on it will be irreversibly deleted. Roughly 420TB of early Bilibili video source files still sit in Sina Cloud S3 buckets, and the Archive Team's distributed archiving project reports it has already rescued about 680TB of data and is 96.26% complete. The shutdown marks the end of China's earliest PaaS service and puts a large slice of early Chinese video-internet history at risk, since Bilibili relied on Sina Cloud for early video source storage. It also highlights how volunteer-led digital preservation efforts are often the last line of defense when commercial cloud services are retired and their storage simply deleted. The Archive Team project is a crowd-sourced crawl racing against the deadline, and the reported figures (96.26% done, ~680TB rescued, ~420TB still remaining) suggest a slice of the material may not be captured in time. The data lives in S3-style object storage buckets, meaning once the buckets are deleted there is no built-in recovery path unless an independent copy exists.

**Background**: PaaS (Platform as a Service) lets developers deploy and run applications without managing servers, and Sina App Engine, launched in 2009, was China's first such platform, attracting many developers with its low cost and zero-ops model. ## [Micron unveils world's first 512 GB DDR5 RDIMM, targets 2027 production](https://videocardz.com/newz/micron-says-worlds-first-512gb-ddr5-module-will-be-production-ready-for-2027) ⭐️ 8.0/10

Micron says it has demonstrated the world's first 512 GB DDR5 RDIMM for servers, a module that runs at up to 9200 MT/s and is built from 3D-stacked DRAM dies. The company says AMD and Intel are validating the module for future server platforms, with production readiness targeted for 2027. Quadrupling the capacity of a single memory module would let a 24-module server reach 12 TB of memory, directly addressing the memory-capacity wall that constrains large database, virtualization and AI inference workloads in datacenters. Micron also claims a power advantage, so the announcement points to denser servers that need less energy per gigabyte rather than simply more DIMM slots. Micron claims a single 512 GB module draws 16 W, compared with 44.2 W for four equivalent 128 GB modules — a reduction of more than 60%. The catch is timing: production readiness is only expected in 2027, and the module still depends on AMD and Intel platform validation, so it is a roadmap announcement rather than a shipping product.

telegram · zaihuapd · Sep 16, 16:15

**Background**: DDR5 is the current generation of main memory used in servers and PCs, and RDIMM (registered DIMM) is the server-oriented variant in which a register chip sits between the DRAM and the memory controller, re-driving signals so a system can host more modules stably than with unregistered memory. 3D stacking — bonding multiple DRAM dies vertically and connecting them with through-silicon vias — is the same family of techniques popularized by High Bandwidth Memory (HBM), which stacks DRAM dies for GPUs and AI accelerators; Micron is applying that idea to conventional, socketed server memory. Capacity per module has historically been limited by how many DRAM dies can be placed on a single board, which is why stacking matters for reaching 512 GB in one RDIMM.
